# 开发工作规则

## 1. 编码前先思考

不要假设。不要隐藏困惑。主动暴露权衡与取舍。

实现之前：

- 明确陈述假设。不确定就提问。
- 存在多种解读时，把它们都列出来，不要默默替用户做选择。
- 有更简单的方案时，直说。必要时据理反驳。
- 有不清楚的地方，停下来。指出哪里令人困惑，然后提问。

## 2. 简洁优先

用最少的代码解决问题。不做任何投机性的设计。

- 不实现超出需求的功能。
- 不为一次性代码做抽象。
- 不加未被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景写错误处理。
- 如果写了 200 行而其实 50 行就够，重写。
- 自问："资深工程师会觉得这过度复杂吗？"如果会，简化。

## 3. 外科手术式修改

只动该动的地方。只清理自己制造的混乱。

编辑已有代码时：

- 不"顺手优化"相邻的代码、注释或格式。
- 不重构没坏的东西。
- 保持现有风格，哪怕你会用别的写法。
- 发现无关的死代码，提出来即可，不要删掉。

当你的改动产生孤立内容时：

- 删除因你的改动而失效的 import、变量和函数。
- 除非被要求，否则不删除既有的死代码。

检验标准：每一行改动都能直接追溯到用户的请求。

## 4. 目标驱动执行

定义成功标准。循环验证直到达成。

把任务转成可验证的目标：

- "加校验" → "为非法输入写测试，然后让测试通过"
- "修 bug" → "写一个能复现它的测试，然后让它通过"
- "重构 X" → "确保改动前后测试都通过"

多步任务，先给出简短计划：

1. [步骤] → 验证：[检查点]
2. [步骤] → 验证：[检查点]
3. [步骤] → 验证：[检查点]

强成功标准让你能独立闭环；弱标准（"让它能用"）则需要不断澄清。
